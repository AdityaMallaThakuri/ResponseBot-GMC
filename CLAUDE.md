# AI Reply Bot (Gamic Media)

## What this is
A service that reads every reply to Gamic Media's cold-email campaigns (Smartlead), decides what the reply is and how well the lead fits, then either drafts the playbook response for Ray to approve in Slack, takes a safe automatic action, or hands the thread to a human. We start with Gamic's own campaigns (names starting "GMC" in Smartlead) before any client.

## Pipeline
Smartlead webhook -> ingest and dedupe -> rules pre-filter -> LLM classifier -> qualifier -> router -> one of three lanes:
1. Draft for approval: template engine -> validator -> Slack card (Approve / Edit / Skip) -> send through Smartlead.
2. Automatic safe action: unsubscribe, pause, or ignore. Always logged and reversible.
3. Human only: Slack alert, no draft.
Every step is logged to Supabase.

## Stack
Python 3.12, FastAPI, Slack Bolt, Supabase Postgres, Anthropic API (small model for classification, mid-size model for the one vertical-specific line), Smartlead API, Google Calendar API, pytest, Docker, Railway. No n8n.

## Hard rules
- Never send an email to a real lead unless the config flag SEND_ENABLED is true. Default is false. A second lock, SEND_ALLOWLIST (comma-separated addresses, empty by default), limits sending to those addresses even when SEND_ENABLED is true; LIVE_SEND_ALL (default false) bypasses it and MUST STAY OFF until we decide to go live. Both the send service and the Smartlead client enforce both locks.
- The template engine may only fill these slots: NAME, DAYTIMEORDAYTIME (two real CST slots from the calendar), links, and one vertical-specific "AI triggers" line. The validator rejects any draft that changes text outside those slots, states a price figure, or makes a claim that is not in the playbook.
- Never invent a price, a case-study number, a time slot or a link. Use only what is in playbook.yaml and the calendar.
- Anything uncertain (low classifier confidence, Smartlead category disagrees, off-script message, validator failure) goes to a human with no draft.
- A model classification with confidence below CLASSIFIER_MIN_CONFIDENCE (default 0.75) goes to human_only with no draft. Rule-based results keep confidence 1.0, and a classifier error also goes to a human (`app/classify/confidence.py`).
- Only do_not_contact may trigger an automatic suppression or unsubscribe. Never auto-suppress or auto-close for not_interested, objection_info or objection_price (`app/classify/policy.py`, `require_auto_action_allowed`). not_interested always goes to a human with no draft: below CLASSIFIER_MIN_CONFIDENCE_NOT_INTERESTED (default 0.90) with no note, at or above it with a "suggest: close" note. Either way a human closes it; no automatic action.
- Do-not-contact replies are suppressed automatically and never drafted. Bounce replies are never drafted (a bounce label does not trigger an automatic suppression).
- Unsubscribe (do_not_contact) replies are suppressed at campaign scope. A global unsubscribe happens only for explicit broad opt-outs (remove me from all lists, do not contact me again, legal threat, spam complaint), and only after a human confirms in Slack. The Smartlead client never goes global on its own. Suppressions record a scope (campaign, client, global).
- Secrets only in .env. Never log full email bodies at INFO level outside Supabase.
- Autonomy levels: notify only, draft for approval, automatic safe action. Auto-send is out of scope until the GMC pilot proves it.

## Labels
The label list lives in app/config/labels.yaml and is finalised in Phase B. Initial set: meeting_request, info_request, free_list_request, price_question, price_and_info, lead_magnet_request, trial_request, booked_confirmation, objection_info, objection_price, not_interested, wrong_person, out_of_office, auto_reply_or_bounce, do_not_contact, off_script.

Classifier v1 (accepted 2026-11-03): deterministic rules first (unsubscribe/stop/remove me, Sendio verify-your-email, "no longer with"), then claude-haiku-5-5 via CLASSIFIER_MODEL with structured JSON output and prompt caching. Claude Haiku 5.5 rejects sampling parameters, so no temperature is sent. Held-out result on the 44 scored rows: 84.1% accuracy, do_not_contact recall 100%. The held-out set (`eval/data/holdout_ids.txt`) is not used for tuning.

## Playbook facts
Offer: fractional deal origination for M&A firms. Calendar link: https://calendly.com/gamicmedia/one-one. Book in CST. Templates T1 to T8 and the objection handlers live in app/config/playbook.yaml, copied word for word from Gamic's M&A GMC reply playbook.

## Smartlead facts
Rate limit 120 requests per minute per key, handle 429 with backoff. Master-inbox fetch: campaign ids max 5, limit max 20, page with offset. Thread text needs the message-history call. Smartlead category tags are a hint only; the bot classifies for itself.
- Inbox response shape (verified on real data): `{"ok": true, "data": [items], "offset", "limit"}`. Each item has `email_lead_id` and `email_lead_map_id` (strings), `email_campaign_id` (int), `lead_email`, and its history under `email_history`. The message-history route returns the same entries under `history`.
- Each history entry has `type` (`SENT` or `REPLY`), `time` (ISO), `email_body` (HTML, must be cleaned), and `stats_id`. The parser raises on any other shape.
- `reply_to_stats_id` is the `stats_id` of the lead's latest REPLY. This is unverified until the first approved staging send.
- Category write-back is off (`CATEGORY_WRITEBACK_ENABLED=false`, and it also needs `SEND_ENABLED`). It is limited to `reply_label` categories in `app/config/smartlead_categories.yaml`; workflow triggers ("Generate ..." and Find Phone Number) and unknown categories are never written. The per-lead category endpoint (method and path) is unverified and not implemented.

## Slack facts
Slack Bolt (async) is mounted on FastAPI at `POST /slack/events`; events and interactivity share that one URL. Bolt verifies every request's signature with SLACK_SIGNING_SECRET and rejects bad ones with 401. Card buttons use the action ids `reply_approve`, `reply_edit`, `reply_skip`. A click acknowledges and updates the message (who clicked, what they chose); as of C2 Approve and Skip also set the card's status in `slack_cards` and nothing else (see Ingest facts). The channel settings SLACK_DRAFT_CHANNEL, SLACK_LOG_CHANNEL, SLACK_ALERT_CHANNEL, SLACK_SHADOW_CHANNEL and SLACK_OPS_CHANNEL are optional until the step that uses them. Never log the bot token, the signing secret or a Slack payload (it can carry email text).

## Ingest facts (C1, C2)
`POST /webhooks/smartlead` (`app/ingest/webhook.py`). Nothing in ingest sends, unsubscribes or writes to Smartlead (including categories); it only reads. SEND_ENABLED stays false. WEBHOOK_SECRET must be at least 32 characters or startup fails. Order: authenticate (401 on a bad or missing secret, no body logged), EMAIL_REPLY only, campaign id must be in GMC_CAMPAIGN_IDS (comma-separated setting; empty means everything is ignored), store in raw_events, answer 200, process in the background. Ignored events get a 200 and a log line and are not stored.
- Authentication: every credential that is present must be valid and at least one must be present: the `X-Smartlead-Signature` header (`sha256=` plus the HMAC-SHA256 of the raw body, keyed with WEBHOOK_SECRET), the `X-Webhook-Secret` header, a `secret_key` body field, or a `?secret=` query parameter (constant-time compare). The query string is redacted from uvicorn's logs (`app/ingest/log_redact.py`) and never stored. UNVERIFIED which one Smartlead sends; Smartlead's docs conflict. `secret_key` is stripped before storing.
- Dedupe: `raw_events.payload_hash` holds the sha256 of the event key, not of the whole body. Key = event_type, campaign_id, the lead (`sl_email_lead_id`, else `lead_id`, `email_lead_id`, else `to_email` lower-cased), the reply's `reply_message.message_id` (else `stats_id`, `message_id`) and its time (`reply_message.time`, else `event_timestamp`, `time_replied`). Without enough fields it falls back to a hash of the whole payload. The payload field names are UNVERIFIED: no real webhook delivery has been captured yet, and `tests/fixtures/real_shapes.json` holds only inbox and history shapes.
- Processing: find the lead (id from the event, else search the campaign's master inbox by `to_email`), fetch `message-history`, `parse_thread`, check the lead's email appears in the thread, upsert the thread and messages. A parse failure or unusable event marks the event processed with `process_error`; a fetch problem records `process_error` and leaves it unprocessed for a retry.
- First reply: a reply is first when the thread had no stored lead reply before this event. A later reply is stored and not classified. The first prospect reply is the earliest REPLY message of the thread.

- C2, classify and post (`app/ingest/classify_step.py`, `app/classify/routing.py`): after C1 stores a thread, the earliest REPLY is classified (rules first, then the model; input is the cleaned reply, the campaign name and the first SENT message) and stored in `classifications` (label, confidence, reason, model, prompt_version, rule_hit). It runs only for a thread with no Slack card yet, so follow-up replies, duplicate events and retried events never classify or post twice. A classifier error stores no classification and posts a human_only notice. Any failure after the thread is stored (Slack down, no channel) is written on the raw event, which stays unprocessed so a retry finishes the job without reclassifying.
- Lanes on the card: `would_suppress` (do_not_contact at 0.75 or above: records an `actions` row of type `would_suppress`, posts a notice, calls nothing), `human_only` (below 0.75, a classifier error, not_interested with "suggest: close" from 0.90, out_of_office, wrong_person, auto_reply_or_bounce, off_script: a notice, no buttons), `draft` (every other label: a card with Approve/Edit/Skip, no draft yet). In `slack_cards` the lane is stored as `auto_action` for would_suppress and `human_only` for the other two (the table requires a draft_id for lane `draft`, so the draft lane is stored as human_only until C3 attaches a draft). The card's channel column holds the Slack channel id.
- Channels: draft-lane cards go to SLACK_DRAFT_CHANNEL; human_only and would_suppress notices go to SLACK_ALERT_CHANNEL, falling back to SLACK_DRAFT_CHANNEL. With neither set the event is left unprocessed with an error.
- Buttons: Approve and Skip only set the card's status (`approved` / `skipped`, first click wins) in `slack_cards`. Edit changes nothing yet. Nothing is sent or suppressed.
- Buttons (C3 updates the line above): on a card with a draft, Approve records a `decisions` row (approved, or edited if a person changed the text, with final_text and edit_distance_pct) and sets the draft and card status; Skip records skipped; nothing is sent (sending is C4). Approve is refused while a placeholder such as [TIME OPTIONS] remains in the text or if the draft failed validation. Edit opens a window; saving stores `drafts.final_text`, re-checks links, prices and numbers and shows warnings (never a block), and Approve still refuses placeholders.

## Drafting facts (C3)
- Templates live in `app/config/playbook.yaml` (schema in its header) and are EMPTY until Aryan or Ray approve wording, so every reply goes to human_only with "No draft: no approved template" until then. `docs/playbook_proposal.md` is a proposal mined from past replies (`scripts/mine_playbook.py`), not approved wording.
- A template fixes structure and wording. Only its declared slots vary: `first_name` and `company` from the thread, `placeholder` (a visible [SLOT NAME] a person fills in), and `model` (a short phrase the model copies from the lead's reply or our email; it is rejected unless those exact words appear there, and never contains digits or links). Several templates for one label: the model only picks an id.
- `app/config/facts.yaml` holds every allowed claim (number, price, result, link) with an id, exact wording, campaign types and `approved`. NOTHING IS APPROVED BY DEFAULT. A draft may only contain a claim that is approved and fits the campaign. The calendar link is the only link allowed, once approved.
- The validator (`app/validate/validator.py`) blocks a draft (it is stored as `failed` and goes to human_only, text not shown) if: a slot is empty or not allowed; a number, price, percentage or link is not in the template wording or an approved claim (clock times and dates are not counted); it is longer than the template's `max_chars`; it contradicts the lead (offering times to a price question, a template for another label); the label is not draftable; confidence is below DRAFT_MIN_CONFIDENCE (default 0.75, blank means 0.75). Placeholders do not block the draft, they block Approve. The result is stored in `drafts.validator_result`, with `drafts.model` (migration 0010). DRAFT_MODEL (default claude-sonnet-5-5) fills slots.

## Sending facts (C4)
Approve on a draft card records the decision and then calls `SendService.send_draft` (`app/send/sender.py`); saving an edit never sends. `SmartleadClient.send_reply` is the only code that sends. A reply is sent only if every check passes; the first failure is recorded in `actions` (type `send`, `details.result` = `blocked_<reason>`) and nothing is sent: SEND_ENABLED is true; a person approved it (a `decisions` row whose `decided_by` is a Slack user id, and the draft is `approved`); no placeholder such as [TIME OPTIONS] remains; the validator on the final text, including edits, finds no link, price or number outside the template wording and approved facts (an edit only warns, but cannot be sent); the lead is the sender of the reply we answer and the campaign is in GMC_CAMPAIGN_IDS; the recipient is in SEND_ALLOWLIST (or LIVE_SEND_ALL is on); and the draft moves `approved` to `sent` in one conditional UPDATE (`claim_draft`), so two clicks cannot both send. A failed send moves it back to `approved` (retryable, `result: failed`, the card gets a Retry send button). The body is never logged or stored in `actions`; only ids, a masked recipient and a result code are. The reply goes to the stats_id of the lead's newest REPLY: UNVERIFIED until a real test send (`scripts/check_reply_target.py` shows it read-only). The body is sent as simple HTML (paragraphs): also unverified. See `docs/safe_send_test.md`.

## Data model
Supabase Postgres. SQL lives in db/migrations (numbered, applied in order by hand, see docs/apply_migrations.md); `python scripts/check_schema.py` validates them against this section.
Tables: raw_events, threads, messages, classifications, qualifications, drafts, slack_cards, actions, suppressions, retry_queue, eval_results, decisions, gold_labels.
- Every table has a uuid primary key and created_at. Row level security is on with no policies: only the service key reads or writes.
- `stats_id` is NOT unique per message (a SENT and its REPLY can share one). `messages` is unique on (thread_id, direction, sent_at, message_id), so a replayed webhook never duplicates or drops a message.
- `threads` is unique on (email_lead_id, email_campaign_id). `raw_events` is unique on (source, payload_hash).
- A draft that failed the validator can only be skipped or failed, never approved or sent.
- `decisions` holds the one human decision per draft (unique on draft_id, so the first Slack click wins): approved, edited or skipped, with skip_reason, final_text, edit_distance_pct and the sent message. `gold_labels` holds human labels (message type, verdict, template T1 to T8) per thread and labeler, for the eval replay.
- `drafts.template_version` records which version of playbook.yaml produced a draft. `classifications.extracted_facts` holds structured facts from a reply (out-of-office return date, referred contact). `threads.vertical` holds the lead's vertical.
- `actions.type` also allows `would_suppress` (migration 0009): a decision recorded while sending is off. Apply 0009 before the first live do_not_contact reply. Migration 0010 adds `drafts.model` and `drafts.validator_result`; apply it before drafting is switched on.
- Decision: no templates table and no events table. Templates stay in app/config/playbook.yaml, and git is their version history; raw_events already records every incoming payload.
- Every new table's migration must also enable RLS and revoke anon and authenticated access; `scripts/check_schema.py` fails otherwise.
- Suppressions keep scope (campaign, client, global) with CHECK constraints; global needs confirmed_by.
